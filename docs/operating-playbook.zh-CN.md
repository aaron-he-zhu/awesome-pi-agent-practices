# Pi 运行手册

<!-- sync:playbook-intro -->

本手册把仓库中的三十条实践连成一个完整运行闭环，适用于有人监督的工作、无人值守自动化、定制能力和应用嵌入。它约束的是人员与宿主应用的工作流，**不表示** Pi 会强制执行审批、隔离、最小权限、审查或留存策略。

P01–P30 的理由与一手证据见[实践指南](practice-guide.zh-CN.md)，机制和所有权边界见[架构图谱](architecture.zh-CN.md)，任何关卡失败时使用[故障排查手册](troubleshooting.zh-CN.md)。

本仓库的稳定参考版本为 Pi v0.83.0。实际使用时，应针对正在运行的版本重新核对命令、默认值、模型服务行为和接口。

<!-- sync:playbook-contract -->

## 运行约定

每次运行都应有可识别的负责人、风险等级、执行边界、任务简报、验证方案、长期记录和停止权限。

以下控制由操作人员或宿主应用承担：

- 操作系统、容器、虚拟机或远程沙箱隔离；
- 凭据范围、网络可达范围、挂载和进程权限；
- 审批、变更管理、留存和事件响应；
- 判断模型输出、工具输出和测试是否足以信任；
- 最终审查、交付、回滚和沟通。

Pi 配置、工具允许列表、Project Trust 和资源发现都只是工作流输入，不能替代外部安全边界。

<!-- sync:playbook-how-to-use -->

## 如何使用本手册

1. 先进行风险分级，再选择模式或加载项目资源。
2. 指定负责角色，并记录谁有权停止运行。
3. 分别从运行模式、定制原语和放置/分发三个轴做选择。
4. 依次通过八个阶段，不得默默跳过关卡。
5. 把每个阶段要求的产物保存在任务输出旁。
6. 触发停止条件时，保留证据并使用相应的[隔离阶梯](troubleshooting.zh-CN.md#隔离阶梯)。

小任务可以由同一人兼任多个角色，各项产物也可以只是简短的 Markdown 小节，但所有控制问题仍须得到明确回答。

## 风险分级

### 风险维度

分级应以可信的最高暴露为准，而不是以希望系统如何表现为准。

| 维度 | 较低暴露 | 较高暴露 |
| --- | --- | --- |
| 来源可信度 | 已知仓库和已审查指令 | 未知或对抗性仓库、提示词或 Package |
| 执行能力 | 只读检查 | Shell、写入、生成代码、生命周期脚本或高权限工具 |
| 数据 | 公开 Fixture | 私有源码、个人数据、受监管数据或凭据 |
| 可达范围 | 无 Secret/Network 的可丢弃目录 | Home 目录、Host Socket、宽泛挂载、生产网络 |
| 监督 | 人类观察每个重大操作 | 无人值守、定时、排队或长时间运行 |
| 可逆性 | 干净 Branch/Worktree，可确定性重建 | Dirty Tree、外部副作用、破坏性迁移 |
| 分发 | 内建行为和固定版本的本地文本 | 第三方运行时代码、移动 Ref、传递依赖 |
| 影响 | 本地实验 | 共享分支、Release、生产服务或外部发布 |

### 风险等级

| 等级 | 典型场景 | 最低边界 | 审批与证据 |
| --- | --- | --- | --- |
| R0 — 观察 | 公开文件、无 Secret、只读问题 | 可丢弃或已知目录；只读型工具 | 操作人员记录来源、版本与结果 |
| R1 — 本地可逆 | 在可信仓库中有人监督地修改 | 可恢复 Git 状态和范围受限的凭据 | 操作人员审查 Diff 和已命名检查 |
| R2 — 隔离敏感 | 未知仓库、第三方 Package、私有数据、宽泛工具，或已隔离的低影响无人值守工作 | Container、VM、Micro-VM、远程沙箱或同等 OS 策略 | 风险负责人批准边界与留存证据 |
| R3 — 高影响 | 生产、发布、破坏性或其他高影响外部副作用；或无人值守工作叠加高权限身份、敏感数据、宽泛可达范围或难回滚影响 | 专用身份和隔离环境，显式控制出站、挂载和 Secret | 独立审查、已演练回滚和事件渠道 |

任一维度向高暴露移动都必须重新分级，但无人值守观察本身并不会自动成为 R3。R3
用于高影响组合，尤其是无人值守执行再叠加高权限、破坏性、生产、敏感数据或难回滚
权限。只有改变了环境或范围才能降低等级，不能因为模型或 Package 看起来行为良好
就降低等级。

### 分级关卡

**入口：**一项请求、目标仓库、预期输出和已知执行环境。

**动作：**逐项评估风险维度；找出不可逆操作；列出数据与凭据；确定 R0–R3；把假设记录到[任务简报](../templates/task-brief.zh-CN.md)和[运行清单](../templates/run-manifest.zh-CN.md)。

**产物：**风险决定、理由、必需控制、批准者和复审有效期。

**退出：**选定边界已经可用，每项必需控制都有负责人。

**停止：**无法识别数据、凭据、外部副作用或回滚路径；无法提供所需边界；或 R3 没有独立批准者。

<!-- sync:playbook-risk-controls -->

### 各等级最低控制

| 控制 | R0 | R1 | R2 | R3 |
| --- | --- | --- | --- | --- |
| 版本记录 | 必需 | 必需 | 必需 | 必需 |
| Git 或 Fixture 基线 | Fixture | 必需 | 必需 | 必需，并保护集成分支 |
| 项目资源审查 | 加载时需要 | 必需 | 批准前必需 | 必需，并经独立批准 |
| OS 隔离 | 可选 | 按暴露决定 | 必需 | 必需且经过测试 |
| 任务专用凭据 | 优先不使用 | 按需 | 必需 | 专用、短期、受监控 |
| 网络策略 | 不得有意外可达范围 | 记录必需 Endpoint | 可行时使用 Allowlist | 显式 Allowlist 与事件监控 |
| 人类监督 | 完成时检查 | 重大修改期间监督 | 在关卡监督 | 外部副作用前独立把关 |
| 回滚演练 | 可重建 Fixture | 明确 Git 回滚 | 已测试清理 | 已演练服务/数据回滚 |
| 证据留存 | 结果摘要 | 清单、Diff、检查 | 脱敏证据包 | 按留存策略保存审计包 |

## 角色与责任

| 角色 | 责任 |
| --- | --- |
| 请求者 | 定义期望结果、业务背景和可接受影响。 |
| 操作人员 | 启动并引导 Pi，观察工具使用，确保运行不越出范围。 |
| 风险负责人 | 接受剩余的安全、隐私、运行和供应链风险。 |
| 审查者 | 独立检查任务简报、Diff、证据和验收结果。 |
| 平台负责人 | 负责沙箱、身份、网络、存储、日志和宿主生命周期。 |
| 维护者 | 负责仓库约定、集成质量和回滚准备。 |
| 事件联系人 | 停止条件表明可能造成损害时接收私密升级。 |

R0/R1 中一人可以兼任多个角色。R3 中，操作人员不应是外部副作用或回滚方案的唯一批准者。

### RACI 矩阵

`A` 表示最终负责，`R` 表示执行，`C` 表示征询，`I` 表示知会。

| 阶段 | 请求者 | 操作人员 | 风险负责人 | 审查者 | 平台负责人 | 维护者 |
| --- | --- | --- | --- | --- | --- | --- |
| 1. 接收与分级 | A | R | C | I | C | C |
| 2. 建立基线与隔离 | I | R | A | C | R | C |
| 3. 简报与上下文 | A | R | C | C | I | C |
| 4. 只读勘察与计划 | C | R | I | C | I | A |
| 5. 执行与协调 | I | R | C | I | C | A |
| 6. 验证与诊断 | C | R | I | A | C | R |
| 7. 交付与清理 | A | R | C | A | C | R |
| 8. 留存、学习与升级 | I | R | A | C | R | A |

**入口：**风险等级所要求的角色已经对应到具体人员或团队。

**动作：**补齐无人负责的环节，规定审批响应时间，并记录谁能中止工具、撤销凭据、拒绝交付和恢复环境。

**产物：**任务专用 RACI 或同等的责任记录。

**退出：**每个关卡和外部副作用都有一位最终负责人。

**停止：**无人能批准边界、审查高影响变更或执行回滚。

## 三轴运行决策

不要把所有 Pi 能力放在同一条“能力阶梯”上。应独立选择运行模式、定制原语和放置/分发方式。

### A 轴 — 运行与集成模式

| 模式 | 适用场景 | 所有者必须提供 | 不适用场景 |
| --- | --- | --- | --- |
| Interactive | 人类在 TUI 中监督编码任务 | 引导、审查、终端兼容和清理 | 作业不能等待人类，或需要解析 TUI 输出 |
| Print（`-p`） | 一个 Prompt 只需一个最终输出 | 显式 Model、Tool、Trust、Session、cwd 和退出策略 | 需要双向控制或完整事件历史 |
| JSON | 程序消费一次运行的事件流 | Streaming Parser、stderr 处理、部分/错误事件策略 | Controller 必须在运行中发命令 |
| 已发布 CLI RPC | 非 Node Controller 或替代 UI 托管长生命周期子进程 | LF Framing、关联、取消、stderr Drain、重启、版本固定 | 进程内 TypeScript 托管更简单 |
| SDK | TypeScript Host 拥有 Session、Resource、Tool 与 Event | Policy、Credential、Persistence、Backpressure、Subscription、Dispose | 隔离必须依赖进程边界 |

使用[P25–P27](practice-guide.zh-CN.md#自动化与嵌入)和[集成模式架构](architecture.zh-CN.md#集成模式)。非交互运行本身不代表无 Session、无项目资源或无环境权限。

### B 轴 — 定制原语

| 需求 | 满足需求的最小原语 | 审查重点 |
| --- | --- | --- |
| 稳定仓库指引 | `AGENTS.md` 或 `CLAUDE.md` | 作用域、优先级、长期真实性、Prompt Injection 风险 |
| 显式复用文本 | Prompt Template | 参数、展开结果、意外扩大范围 |
| 按需工作流、参考资料或辅助脚本 | Skill | 指令、脚本、Asset、可执行与数据访问 |
| Runtime Event、Tool、UI、Policy 或 Provider | Extension | 进程内代码、生命周期、权限、失败行为 |

从[P07–P11](practice-guide.zh-CN.md#任务与上下文设计)开始。按照[P21–P24](practice-guide.zh-CN.md#extension-与-package)先用文本验证，再引入运行时代码；采用可执行制品前使用[Extension 审查](extension-review.zh-CN.md)。

### C 轴 — 放置与分发

| 放置方式 | 适用场景 | 主要控制 |
| --- | --- | --- |
| 任务内文本 | 指令只属于本次运行 | 放入任务简报或 Prompt，与输出一起审查 |
| 仓库资源 | 规则适用于本仓库贡献者 | 纳入版本控制、缩小作用域、审查项目资源加载 |
| 用户/全局资源 | 行为应随一个操作人员跨项目生效 | 审计它对未知仓库及 Trust 时序的影响 |
| 来自 npm/Git/本地路径的 Pi Package | 多种资源需要可重复分发 | 固定身份/Ref，检查依赖/脚本，测试安装与移除 |
| 宿主应用代码 | 产品自己承担编排或集成 | 按应用管理 Policy、Secret、Test 与生命周期 |

### 决策关卡

**入口：**可测试的能力需求和 R0–R3 分级。

**动作：**在每个相关轴各选一行；说明更小原语或更简单模式为何不合适；记录版本与所有权；审查所有可执行输入。

**产物：**例如 `Interactive + Skill + Repository` 或 `RPC + 无 Pi 定制 + Host Application` 的三轴决定。

**退出：**选定组合有明确负责人、测试方案、安装/启动路径和移除/关闭路径。

**停止：**只按流行度选择；移动 Artifact 无法固定；运行时代码没有生命周期负责人；或所选模式无法实现宿主要求的策略。

## 八阶段运行闭环

每个阶段都消费上一阶段的产物。退出关卡失败时，应返回最早发生假设变化的阶段。

<!-- sync:playbook-stage-1 -->

### 阶段 1 — 接收与分级

**入口：**至少包含期望结果和目标仓库/系统的请求。

**动作：**澄清当前与期望行为；列出范围内外路径；识别外部系统；确定 R0–R3；分配 RACI；规定最大可接受时间、费用、数据暴露和外部副作用。

使用[任务简报模板](../templates/task-brief.zh-CN.md)。对未知事实给出链接或待确认项，不要默默把它们变成假设。

**产物：**已批准的任务简报、风险等级、责任、预算和停止权限。

**退出：**范围与验收可测试，所需控制均可用。

**停止：**目标冲突、权限不明、生产影响未定义、审查者不可用，或有人要求隐瞒重大风险。

<!-- sync:playbook-stage-2 -->

### 阶段 2 — 建立基线与隔离

**入口：**已批准的简报和风险决定。

**动作：**应用[P01–P06](practice-guide.zh-CN.md#baseline-and-recovery)：记录执行环境、检查 Git 状态、创建可恢复的 Branch/Worktree 或 Fixture、审查 Project Trust 输入、缩小凭据/挂载/网络，并固定所有 Package 或 Extension。

至少记录：

```bash
pi --version
node --version
git status --short
git rev-parse --show-toplevel
git rev-parse HEAD
```

处理不可信或无人值守工作时，应在 Pi 接触仓库前建立并测试外部 OS 边界。测试结果应证明无关文件、凭据、Host Socket 和未批准目标均不可访问。

**产物：**填写完成的[运行清单](../templates/run-manifest.zh-CN.md)、Git/Fixture 基线、隔离决定、资源清单和回滚点。

**退出：**另一位操作人员能够重建环境，并且恢复时不会丢弃预先存在的工作。

**停止：**Dirty State 无法归属；凭据范围超过任务；不可信代码能访问 Host； Artifact 身份不确定；或回滚尚未证明。

<!-- sync:playbook-stage-3 -->

### 阶段 3 — 简报、上下文与能力设计

**入口：**可复现基线和有效边界。

**动作：**应用[P07–P11](practice-guide.zh-CN.md#任务与上下文设计)。盘点适用的 `AGENTS.md`/`CLAUDE.md`、Settings、Prompt、Skill、Theme、Extension、Package、 Tool、Provider/Model、Session Behavior 和 Working Directory。移除无关上下文，按上述三轴选择能力。

仓库指令可从[AGENTS.md 模板](../templates/AGENTS.zh-CN.md)开始，只保留会改变执行方式、且长期有效的事实。非交互工作应显式说明 Trust、Context、Tool、Model、cwd 和 Session 策略。

**产物：**上下文/资源清单、三轴决定、能力允许列表和验收命令方案。

**退出：**每项加载输入和可执行能力都有理由和负责人，任务仍符合批准的风险等级。

**停止：**冲突指令无法解决；项目资源未经审查；同名自定义工具无法解释；或没有文本无法满足的需求，却选择了运行时原语。

<!-- sync:playbook-stage-4 -->

### 阶段 4 — 只读勘察与计划

**入口：**已批准的上下文与能力集合。

**动作：**按照[P09](practice-guide.zh-CN.md#p09--先只读勘察再扩大能力)从只读开始。梳理相关文件、所有权边界、测试、生成制品、迁移路径和可能的回滚方式。需要时把完整本地输出保存在模型上下文之外，同时把决定性证据提供给模型。

下面是一个经过源码审查的基线。先按照[干净基线](troubleshooting.zh-CN.md#干净基线)
在相同资源控制下枚举真实条目，再替换 `PROVIDER` 与 `MODEL`：

```bash
pi --offline --no-approve --no-context-files --no-extensions --no-skills \
  --no-prompt-templates --no-themes --no-session \
  --tools read,grep,find,ls \
  --provider PROVIDER --model MODEL -p \
  "梳理相关代码并提出检查方案。"
```

调整这些参数时必须说明理由：它们控制 Pi 启动网络操作、资源加载与已注册工具，
不控制 Provider Traffic 或操作系统权限。

**产物：**代码/系统地图、拟议修改、依赖顺序、已命名检查、未知项和能力扩大申请。

**退出：**审查者能把每项修改映射到范围，把每项检查映射到验收标准。

**停止：**观察到的系统与简报矛盾；缺少必需数据；第一次写入不可逆；或计划需要更高风险等级。

<!-- sync:playbook-stage-5 -->

### 阶段 5 — 执行与协调

**入口：**已审查计划、恢复点、最低写入能力，以及与风险相匹配的有效监督。

**动作：**应用[P12–P20](practice-guide.zh-CN.md#任务执行中)：每个 Session 只保留一个连贯目标，区分 Steering 与排队的 Follow-up，限制命令与重试，关注输出截断，把长期决定写入文件，把跨模型 Handoff 视为尽力而为。涉及运行时代码或嵌入时应用 P22–P27。

每个重大操作都应：

1. 说明预期修改和受影响路径/系统；
2. 执行前立即检查前置条件；
3. 执行最小、可逆的一步；
4. 检查结果、stderr/Event 和仓库/外部状态；
5. 扩大范围前保存检查点。

**产物：**聚焦的 Diff 或外部变更集、决定日志、检查点记录、命令/事件摘要和更新后的未知项。

**退出：**计划内修改已经完成，没有无法解释的副作用，环境已可供独立验证。

**停止：**工具行为与描述不符；输出被截断且无法继续；重试超过预算；取消失败；凭据进入输出；Session 丢失关键不变量；或变更越出范围。

<!-- sync:playbook-stage-6 -->

### 阶段 6 — 验证与诊断

**入口：**候选变更和未被修改的验收标准。

**动作：**从窄到宽运行检查：目标复现、单元/组件检查、静态分析、集成检查和最终 Diff 审查。比较期望与实际输出，包括 Exit Status 和负向案例。

检查失败时保留失败案例，并应用[P28](practice-guide.zh-CN.md#p28--用隔离阶梯诊断)和[故障排查隔离阶梯](troubleshooting.zh-CN.md#隔离阶梯)。每次只改变一个变量，不能通过修改验收标准来迎合输出。

Extension/Package 工作在成为正式推荐或广泛发布前，应完成[亲测审查模板](../templates/hands-on-review.zh-CN.md)。

**产物：**验证矩阵，记录命令/输入、期望结果、实际结果、状态、环境与证据位置；以及经过审查的最终 Diff。

**退出：**已命名验收检查通过，负向与回滚路径可信，跳过的检查和剩余风险得到负责人接受。

**停止：**安全边界失效；证据无法复现；测试不稳定且无法在预算内诊断；源码与 Artifact Provenance 不一致；或审查者无法解释 Diff。

<!-- sync:playbook-stage-7 -->

### 阶段 7 — 交付与清理

**入口：**验证通过的结果和已批准的剩余风险。

**动作：**交付说明先写结果，再列出变更路径或外部副作用、检查摘要、跳过的检查、风险和回滚。分离预先存在的修改。移除临时制品并撤销任务凭据。按照[P16](practice-guide.zh-CN.md#p16--导出或分享前清理-session)在分享前检查 Session、 Log、Export 和 Link。

不能因为模型生成了一份看似合理的报告就直接发布或提交上游。按照[P30](practice-guide.zh-CN.md#p30--经过人类复现与审查后再向上游贡献)取得人类复现与审查。

**产物：**交付包、脱敏证据、清理记录、凭据处置记录和已测试回滚步骤。

**退出：**请求者能验证结果，维护者能继续工作，平台负责人能说明留存数据和仍有效访问权限。

**停止：**可能包含 Secret 或 Private Source；不知道 Share Link 的可见性或撤销方式；回滚含糊；或交付会绕过必需审查/变更控制。

<!-- sync:playbook-stage-8 -->

### 阶段 8 — 留存、学习与升级

**入口：**交付已被接受，清理已经完成。

**动作：**只按仓库、法律、安全或运行策略保留制品。对失败记录根因和预防措施。把长期有效的指令写入经过审查的仓库文件，而不是只留在 Session History。让临时例外和凭据过期。为版本敏感行为、Package、Extension 和 Provider/Model 假设安排复测。

升级时遵循[P29](practice-guide.zh-CN.md#p29--通过固定分阶段可逆的路径升级)：记录前后版本，在可丢弃环境测试，运行 Smoke Matrix，分阶段发布，并演练回滚。

**产物：**留存决定、经验/ADR、回归测试或后续项、过期/复测触发器和已关闭任务记录。

**退出：**长期知识可审查，临时访问已移除，留存数据有负责人和有效期，下一次版本敏感复审有触发器。

**停止：**策略要求删除但无法确认；事件仍未关闭；临时控制没有有效期；或经验记录会暴露 Secret/Private Material。

## 检查点与并行工作

Pi Session 分支和文件系统分支解决的是不同问题。`/tree`、`/fork`、`/clone` 不会恢复文件，也不会隔离并发修改。本手册不假设外部或第三方多 Agent 编排是 Pi 内建控制；协调方必须负责隔离、调度、取消和合并。

### 并行工作关卡

**入口：**计划中存在两个或更多可以独立验证的工作单元。

**动作：**为每个单元指定一个目标、Branch/Worktree 或互不相交的写集合、负责人、输入 Commit、验收检查、预算和集成顺序。识别共享的生成文件、Schema、Lockfile、 Database、Port、Credential 和 Rate Limit。串行化共享的 Read-modify-write 窗口。

使用所有权台账：

| 单元 | 负责人/Session | Branch/Worktree | 写集合 | 依赖 | 检查 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例 A | 具名操作人员 | 精确路径/Ref | 路径或外部系统 | 无 | 命令/结果 | 计划中 |
| 示例 B | 具名操作人员 | 精确路径/Ref | 路径或外部系统 | A 的接口 | 命令/结果 | 阻塞 |

**产物：**所有权台账、依赖图、检查点 Ref、合并顺序和冲突策略。

**退出：**各单元基于预期基线集成，共享不变量通过，合并后的 Diff 经过全新审查。

**停止：**两个写入者在没有串行化的情况下拥有同一可变状态；单元无法取消；依赖发生变化却未通知；或集成要求丢弃用户已有工作。

### 长时间工作关卡

**入口：**预计时长超过一个监督窗口、一个模型 Context 或一个 Provider/Tool 重试预算。

**动作：**定义 Wall-clock、Token/Cost、Retry 和外部副作用预算。在语义里程碑保存有限检查点。Compaction 或 Handoff 前，把决定、当前状态、下一步和回滚写到模型可见上下文之外。规定 Heartbeat、Cancellation、Restart 和过期工作策略。每次 Resume 都重新验证凭据与目标状态。

**产物：**预算、检查点计划、长期状态记录、恢复前置条件以及取消/清理步骤。

**退出：**工作可以从已验证检查点停止和恢复，不依赖隐藏 Session 状态，也不会重复产生外部副作用。

**停止：**在约定窗口内没有 Heartbeat；预算耗尽；同类失败反复重试；检查点无法重建；目标已经变化；或操作人员无法重新取得控制。

## 数据、凭据、Session 与日志

### 数据分类

| 等级 | 示例 | 默认处理方式 |
| --- | --- | --- |
| 公开 | 公开仓库、公开文档、合成 Fixture | 记录来源；仍检查恶意指令 |
| 内部 | 非公开代码、路径、Hostname、设计说明 | 最小 Context、批准的 Provider/Host、受控留存 |
| 敏感 | 个人数据、客户数据、安全发现 | 隔离处理、明确负责人、脱敏和删除计划 |
| Secret | API Key、Bearer Token、Cookie、Private Key | 不进入 Prompt/Log；窄范围注入、轮换并撤销 |

**入口：**数据清单、Provider/Host 路径、留存策略和任务风险。

**动作：**减少进入模型 Context 的数据；使用稳定脱敏标签；任务凭据与个人凭据分离；限制 Environment、Mount、Socket 和 Network；避免 Shell Tracing 或 Debug Output 打印 Secret；Tool Output 进入 Session/Export 前先检查。

每个凭据都要记录负责人、用途、Scope、注入路径、有效期、轮换/撤销动作和处置证明。禁用 Telemetry 不等于禁用 Provider Traffic。

Session JSONL、HTML Export、Debug Log、Tool-output File、RPC/JSON Event、 Screenshot 和 Share Link 都应视为可能敏感。`!!` 控制的是模型 Context，不一定控制持久化或 Export。

**产物：**Data Flow 说明、凭据登记、脱敏映射、留存/删除决定和脱敏证据位置。

**退出：**只剩批准的数据路径，每个凭据均可追踪，留存制品有负责人、可见性、有效期和删除路径。

**停止：**数据等级未知；发生意外出站；Secret 进入 Transcript/Log；无法撤销； Provider/Region 未批准；或 Share Link 可见性不确定。

## 验证与交付标准

验证既要证明请求结果，也要约束意外修改。“Agent 说已经通过”不能作为证据。

### 验证矩阵

| 层 | 必须回答的问题 | 证据 |
| --- | --- | --- |
| 复现 | 修改前是否存在原始失败？ | 最小命令/输入和捕获结果 |
| 聚焦行为 | 最小相关检查现在是否通过？ | 精确命令、状态和输出摘要 |
| 负向行为 | 拒绝、非法、取消和超大案例是否安全？ | 预期失败和保留的错误类别 |
| 集成 | 受影响边界是否仍能协作？ | 固定版本 Fixture 或集成结果 |
| 回归 | 邻近的既有检查是否仍通过？ | 已命名 Suite 和环境 |
| Diff | 每项修改是否在范围内、有意且可归属？ | 人工审查 Diff 和文件清单 |
| 安全/数据 | 权限、出站、Secret 或留存假设是否变化？ | 边界测试和数据/凭据记录 |
| 恢复 | 能否回滚而不丢失无关工作？ | 已演练命令或恢复步骤 |

### 交付包

完整交付应包含：

1. 结果和影响；
2. 精确变更路径、制品、配置或外部系统；
3. 前后环境与不可变 Ref；
4. 包含命令和结果的验收矩阵；
5. 被跳过、部分完成或不稳定的检查及理由；
6. 剩余安全、隐私、兼容性、费用和运行风险；
7. 清理和凭据处置；
8. 回滚触发条件与步骤；
9. 留存证据位置和有效期；
10. 审查者、批准者和后续负责人。

**入口：**阶段 6 的证据和已批准范围。

**动作：**把交付包与任务简报、运行清单逐项核对；让审查者抽查证据，并独立执行关键检查。

**产物：**签名或以其他方式可归属的交付包。

**退出：**请求者接受结果，审查者接受证据，风险负责人接受已披露剩余风险。

**停止：**验收依赖无法核验的模型叙述、可变链接、缺失版本、无法解释的变更或缺少回滚。

## 单页运行检查

开始前：

- [ ]任务、范围、负责人、RACI、风险、预算和停止权限明确。
- [ ] Pi/Runtime/Model/Resource 版本和 Git 基线已记录。
- [ ] Trust、Context、Tool、Package、Credential、Mount、Network 和 Session
      行为均为有意选择。
- [ ] Mode、Customization 和 Placement 决定已分别记录。
- [ ]验收、负向检查、恢复和证据位置均已命名。

交付前：

- [ ]原始失败和请求结果都有可复现证据。
- [ ]已命名检查通过；跳过的检查和不确定性已披露。
- [ ]最终 Diff/外部副作用不含无法解释或无关修改。
- [ ] Secret、Session、Log、Export、Link 和临时制品已处理。
- [ ]凭据撤销、清理、回滚、留存和复测均有负责人。
- [ ]人类审查者能够解释结论，并能从交付包继续工作。

任何方框无法确认时，都应返回最早受影响的阶段，而不是默默降低完成标准。
